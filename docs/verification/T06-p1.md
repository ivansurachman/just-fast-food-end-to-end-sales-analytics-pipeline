## 1. Each mart equals the same measure computed from the facts

Both directions of `EXCEPT`, whole tables, run inside the scheduler container against
`/opt/airflow/duckdb/jff.duckdb` (read-only). The comparison queries, one per mart:

```sql
-- mart_sales_day_branch_channel: all orders, completed money only
select cast(order_ts_local as date), branch_key, channel_key,
       count(*), count(*) filter (where status_final = 'completed'),
       count(*) filter (where status_final = 'cancelled'),
       count(*) filter (where status_final = 'refunded'),
       coalesce(sum(gross_amount)      filter (where status_final = 'completed'), 0),
       coalesce(sum(discount_amount)   filter (where status_final = 'completed'), 0),
       coalesce(sum(net_amount)        filter (where status_final = 'completed'), 0),
       coalesce(sum(cogs_amount)       filter (where status_final = 'completed'), 0),
       coalesce(sum(platform_commission_amount) filter (where status_final = 'completed'), 0)
from fact_order group by 1, 2, 3;

-- mart_hourly
select cast(order_ts_local as date), branch_key, hour_local,
       count(*), count(*) filter (where status_final = 'completed')
from fact_order group by 1, 2, 3;

-- mart_item_day: completed items only
select cast(strptime(cast(date_key as varchar), '%Y%m%d') as date), menu_item_key,
       sum(quantity), sum(line_amount), sum(line_cogs)
from fact_order_item where order_status_final = 'completed' group by 1, 2;

-- mart_promo_day: completed orders
select cast(order_ts_local as date), promo_key, channel_key,
       count(*), sum(gross_amount), sum(discount_amount), sum(net_amount)
from fact_order where status_final = 'completed' group by 1, 2, 3;

-- mart_branch_coverage: the fact joined to completed sales per branch-day
select cast(strptime(cast(b.date_key as varchar), '%Y%m%d') as date), b.branch_key,
       b.is_expected, b.orders_received, b.late_arrival_orders,
       coalesce(s.completed_orders, 0), coalesce(s.net_amount, 0)
from fact_branch_day b
left join (select cast(order_ts_local as date) as d, branch_key,
                  count(*) filter (where status_final = 'completed') as completed_orders,
                  coalesce(sum(net_amount) filter (where status_final = 'completed'), 0) as net_amount
           from fact_order group by 1, 2) s
       on s.d = cast(strptime(cast(b.date_key as varchar), '%Y%m%d') as date) and s.branch_key = b.branch_key;
```

## 2. Expected versus received branch-days, whole window

`is_expected` comes from `dim_branch.open_date`; the day set is the run window clamped at the first
`fact_order.source_file_date` (2026-10-01), so a day the generator never produced a file for is not
counted. The missing branch-days are compared as *sets* against `dropped_branch_ids` in the manifests:

```sql
with manifests as (
    select regexp_extract(filename, 'dt=([0-9-]+)', 1) as dt, dropped_branch_ids
    from read_json_auto('s3://jff-raw/_manifests/dt=*/manifest.json', filename = true)
),
dropped as (select cast(dt as date) as day, unnest(dropped_branch_ids) as branch_key from manifests),
missing as (
    select cast(strptime(cast(date_key as varchar), '%Y%m%d') as date) as day, branch_key
    from fact_branch_day where is_expected and orders_received = 0
)
select (select count(*) from missing)            as missing,
       (select count(*) from dropped)            as manifest_dropped,
       (select count(*) from (select * from missing except select * from dropped)) as missing_not_dropped,
       (select count(*) from (select * from dropped except select * from missing)) as dropped_not_missing;
```

## Notes and limits

- **The dataset gained one day.** D5 said 46 days (2026-10-01 .. 2026-11-15) when this task ran;
  accepting "one new day" extended the window to 47 (.. 2026-11-16), and Ivan confirmed 47 on 23 Nov
  (section 8 below, and `docs/pipeline-design.md` section 14). The lake went to 48 dates because
  2026-09-30 (late orders of the 10-01 file) has always been a partition.
- **2026-09-30 exists in four marts, not in `mart_branch_coverage`.** The sales, hourly, item and
  promo marts are order-date facts and 09-30 has orders; coverage needs a file date and 09-30 has
  none. Every card filters `order_date >= date '2026-10-01'`, so nothing on a dashboard shows it.
- **`fact_branch_day` spine.** The day set is the run window clamped at the first
  `fact_order.source_file_date`. Without the clamp, the run for 10-01 (window 09-21 .. 10-01) would
  invent 120 missing branch-days for 09-30 and the missing count would no longer equal the manifest
  drops. The earliest order date alone is not enough for the same reason.
- **Filling the marts, and one repair re-run.** The four new tables were empty, so after the models
  existed they were loaded with a wide window (this run also predates the 2026-11-16 day):

